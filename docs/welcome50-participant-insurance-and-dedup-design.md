# WELCOME50 逐位參加者查驗與保險資料：已同意方向，待隔離實作

## 2026-10-20 使用者確認
多人報名需逐位列出參加者姓名；因涉及活動保險，應把必要的保險資料與優惠查驗整合，避免重複填寫。LINE API 仍不串接。

## 現有系統查核
目前 `activity-register.html` 僅有**一組** `full_name`、`birth_date`、`national_id`，同時另有 `quantity`；`insurance_opt_out` 在現行報名流程為整筆布林值。**因此不能宣稱目前已能識別多人報名的每位參加者，或逐人投保。** 現有保險欄位標示選填；不應在未取得明確同意前將其全面改為強制填寫。

## 最小新增資料模型（設計草案，未部署）
- `registrations` 保留原有聯絡人、訂單、付款與取消欄位。
- 新增 `registration_participants` 子表：`id`、`registration_id`、`event_slug`、`participant_index`、`full_name`、`birth_date`、`national_id`（僅必要投保情況保存，應限制讀取）、`insurance_opt_out`、`welcome50_applied`、`welcome50_identity_key`（僅用於伺服器比對，不能顯示給一般管理介面）、建立時間。
- 身分識別：以有效身分證明資料在伺服器端正規化後，透過**金鑰 HMAC** 產生不可逆比對鍵，且綁定活動場次；避免直接以姓名判斷，也不可使用無金鑰 SHA256 代替。
- 必須確保唯一性：每位參加者、每場活動僅可成功使用一次 WELCOME50；在資料庫交易中以部分唯一索引或原子檢查防止並發重複折抵。單靠前端 JS 或先查後寫不夠。
- 逐人查驗不等於全部人都必須有保險：現有保險選填政策若維持，需設計未投保者如何提供最小必要查驗識別資訊；不能以保險用途作為不相關的蒐集理由。若無可用識別資訊，應明確告知無法自動套用該人優惠，而不是暗中放行。
- 適用活動限 `service=city` 且 `welcome50_enabled=true`，日期、優惠碼與每人 NT$50 規則照舊。

## 交易一致性
- 同一個資料庫交易內：鎖活動容量 → 建立訂單 → 寫入所有參加者 → 唯一性驗證 → 保存優惠折扣 → 完成提交；任何錯誤必須全部回滾。
- 同場同一人第二次報名，該人不得再享優惠；同一筆多人訂單有部分重複時，需明確提示並讓使用者確認可折抵的人數，不能默默以原價計算。
- 取消後優惠資格是否恢復，需明確訂定政策並和取消訂單交易一致。
- 訂單原價、折扣、實付及通知信需一致；個資不得寫入 URL、分析事件、一般錯誤日誌或外寄管理通知全文。

## 下一步
1. 先設計不蒐集超額個資的參加者表單與資料庫草案。
2. 建立不含真實身分資料的離線測試案例：同人同場重複、同人不同場、多人成團、取消、同時送出、保險選填。
3. 正式啟用前需完成保險資料用途告知、權限與保存期限審核，以及完整端到端測試。
